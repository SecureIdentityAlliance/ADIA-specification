# Transaction DIDs — Draft Normative Text

Drafted from RK's description: *"Pairwise DIDs are for one-time transactions during verification and they are generated by the Interchange on behalf of the user, not by enterprises."*

This is a working draft for the architect to react to, not a recommendation. §5 records what it costs and what it does not achieve on its own.

---

## 1. Terminology: why this text says "transaction DID"

Two distinct mechanisms are commonly both called pairwise:

| | Scope | Verifier can recognise a returning user | Prevents cross-verifier correlation |
|---|---|---|---|
| **Pairwise DID** | One per relying party, persistent | Yes | Yes |
| **Transaction DID** | One per presentation, ephemeral | **No** | Yes |

RK's description — one-time, per verification — is the second. The current text hedges: §3.19 Note 3 says *"temporary, pairwise DIDs for session use"*, which reads as both.

The distinction is not cosmetic. A Service Provider that maintains an account, a subscription, or any continuity of relationship needs to recognise a returning user. With transaction DIDs it cannot, unless the credential itself carries something stable — which reintroduces the correlator the mechanism exists to remove. **The working group should choose one**, and the choice depends on whether ADIA's Service Providers are one-shot verifiers (age checks, door access) or account-holding relying parties (banks, employers).

The draft below specifies transaction DIDs, per RK. If the answer is pairwise, the changes are noted in §6.

## 2. Draft normative text

### 7.4.4 Transaction DIDs

> **Placement:** insert after the `#did-addressing` anchor, as the last subsection of Identifiers. Section numbers below are correct as of 18 Sep 2026; if the document is renumbered, the anchor is authoritative.

> **§7.4.4.1 Purpose and scope**
>
> A **transaction DID** is a short-lived Decentralized Identifier generated by an Interchange on behalf of a User, used as the subject identifier of a single Verifiable Presentation. Its purpose is to prevent a Service Provider from using the subject identifier to correlate one presentation with another.
>
> A transaction DID is generated by the Interchange's Digital Address Service. A User does not generate one, and a Service Provider MUST NOT generate, assign, or request a specific transaction DID.
>
> Each Digital Address has exactly one primary DID, which is permanent and is the subject of its ADI-ROLE VC. A Digital Address MAY additionally be represented by transaction DIDs, each valid for one presentation.
>
> **§7.4.4.2 Generation**
>
> On receiving a `vc_request` from a Service Provider Agent, and after the User has authorised the presentation under §7.2.4.4, the Digital Address Service MUST:
>
> 1. Generate a fresh key pair inside the Interchange hardware security module. The key MUST be unique to this presentation and MUST NOT be derived from, or linkable to, the primary DID key or any previous transaction key by any party other than the Interchange.
> 2. Construct a transaction DID in the form specified in §7.4.3, whose method-specific identifier is a UUIDv4 and which is marked as transaction-scoped by the `txn` segment. For example: `did:adi:r1:ix1:txn:3b9c1e2a-...`.
> 3. Record the binding `{transaction DID, primary DID, Service Provider DID, timestamp, request nonce}` in the Interchange audit log required by §8.
> 4. Publish a DIDDoc for the transaction DID containing the generated public key, signed by the Interchange, with `validUntil` no later than `iat + 24 hours`.
>
> The Interchange MUST NOT reuse a transaction DID for a second presentation, and MUST NOT issue two transaction DIDs bearing the same public key.
>
> **§7.4.4.3 Use in a presentation**
>
> Where a presentation uses a transaction DID:
>
> 1. The key-binding JWT MUST be signed by the transaction key and its `iss` MUST be the transaction DID.
> 2. The presented credential MUST have been issued with `credentialSubject.id` withheld, and its `cnf` MUST reference the transaction key (see §7.4.4.4). A presentation whose credential carries a stable `credentialSubject.id` MUST NOT be described as unlinkable, and the Interchange MUST NOT represent it as such.
> 3. The presentation MUST carry `adia_subject_scope: "transaction"`. Where the primary DID is the subject, it MUST carry `adia_subject_scope: "primary"`.
>
> A Service Provider MUST treat a transaction DID as valid for the presentation in which it appears and for no other purpose. It MUST NOT store a transaction DID as a persistent account identifier, and MUST NOT expect the same identifier from the same User on a subsequent presentation.
>
> **§7.4.4.4 Credential requirements**
>
> A credential intended for presentation under a transaction DID MUST be issued such that its subject identifier is not disclosed to the verifier. This specification defines one conforming method:
>
> - **Selectively disclosable subject.** The credential is an SD-JWT VC (§6.2) in which `sub` is a selectively disclosable claim. The Holder withholds the `sub` disclosure. The credential's `cnf` is set at issuance to a key the Interchange will use for a single presentation, and the Issuer MUST issue a batch of such credentials, one per intended presentation, each with a distinct `cnf` key.
>
> An Issuer that cannot meet this requirement MUST NOT mark a credential as eligible for transaction-DID presentation, and the Interchange MUST reject a request to present such a credential under a transaction DID.
>
> **§7.4.4.5 Resolution**
>
> A transaction DID resolves through §10.2 in the same way as a primary DID. The Digital Address Service of the issuing Interchange MUST serve its DIDDoc until `validUntil` and MAY return `410 Gone` thereafter. A verifier MUST complete verification of a presentation within the validity window of the transaction DID it carries.
>
> **§7.4.4.6 Accountability**
>
> The binding recorded under §7.4.4.2 item 3 is the sole record linking a transaction DID to a primary DID. The Interchange MUST retain it for the period required by applicable regional law and MUST disclose it only under §8. A transaction DID therefore provides unlinkability with respect to Service Providers, and no unlinkability with respect to the Interchange.

## 3. Data model additions

**`vc_request`** — the Service Provider states whether it requires a persistent identifier:

```json
{
  "aud": "did:adi:r1:ix1:sp-uuid",
  "nonce": "n-0S6_WzA2Mj",
  "exp": 1758240000,
  "schemas_accepted": ["US_Passport"],
  "min_ial": 2, "min_aal": 2, "min_fal": 1,
  "subject_scope_required": "any"
}
```

`subject_scope_required` is `"primary"`, `"transaction"`, or `"any"`. A Service Provider that maintains accounts sets `"primary"`; one performing a one-shot check sets `"transaction"` or `"any"`.

**Presentation** — declares what it used:

```json
{
  "adia_subject_scope": "transaction",
  "iss": "did:adi:r1:ix1:txn:3b9c1e2a-...",
  "nonce": "n-0S6_WzA2Mj",
  "aud": "did:adi:r1:ix1:sp-uuid"
}
```

**§10.3 verification algorithm** gains a step, after step 4 (holder binding):

> 4a. **Subject scope.** If `R.subject_scope_required` is `"primary"`, reject a presentation whose `adia_subject_scope` is `"transaction"`. If `adia_subject_scope` is `"transaction"`, confirm the credential does not disclose a stable subject identifier; if it does, the presentation is not unlinkable and MUST be processed as `"primary"`.

## 5. What this costs, and what it does not achieve alone

**It does not work without batch issuance.** §7.4.4.4 is the load-bearing requirement. While `credentialSubject.id` in B.2.4 is the primary DID, a verifier reads the correlator straight out of the credential body no matter what identifier wraps the presentation. Transaction DIDs without selectively disclosable subjects and per-presentation `cnf` keys are decoration.

That means Issuers must issue **batches** of single-use credentials and Users must manage exhaustion and replenishment. Neither is in the spec. It is real work, and it is the reason most deployed VC systems have not shipped this.

**It requires SD-JWT VC.** Decision D6. If the working group keeps plain JSON-LD credentials, this feature cannot be specified as drafted.

**It breaks returning-user recognition.** Any Service Provider with an account relationship must set `subject_scope_required: "primary"`, which means those transactions get no unlinkability at all. Worth knowing how much of the expected traffic that is before committing to the mechanism.

**The Interchange still sees everything.** §7.4.4.6 says so plainly. This is unlinkability against Service Providers only. The accountability property the architecture is named for requires the Interchange to hold the binding, and those two goals are in direct tension. The spec should state that rather than let a reader infer full unlinkability from the word "privacy preserving".

**The alternative is honest deferral.** Delete the three sentences, state in Privacy Considerations that v3.0 credentials carry a stable subject identifier and that Interchanges observe all transactions, and schedule the mechanism for 3.1 alongside SD-JWT VC and batch issuance. That is a defensible position for a first conformance-testable release, and it is what the register currently recommends.

## 6. If the answer is pairwise rather than one-time

Persistent per-verifier identifiers are a smaller change and preserve returning-user recognition:

- §7.4.4.2 generates a key deterministically from `HMAC(K_user, Service Provider DID)` held in the HSM, so the same Service Provider always sees the same DID and no other does.
- No batch issuance is needed for the identifier itself, though the credential's subject-identifier problem in §5 remains.
- `adia_subject_scope` becomes `"pairwise"`, and §7.4.4.3 item 3's prohibition on persistent storage is removed — a Service Provider is expected to store it as the account key.
- DIDDoc validity becomes the life of the relationship rather than 24 hours.

This is closer to what most systems that ship this feature actually do, and it may be what RK means. Worth asking directly, because the two produce different specifications.
